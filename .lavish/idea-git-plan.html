00

Where the fork is today

Three facts about the current extension shape the whole proposal. Two of them are helpful — the groundwork already exists. One is the constraint everything else has to fit around.

✓
Multi-select already works

The commit list already supports ⌘-click and ⇧-click selection, and the detail pane already merges the file changes of several selected commits. Nothing new is needed to pick two commits.

✓
A comparison surface exists

Branch-vs-branch comparison already opens its own window with two commit logs. It is scoped to refs, not arbitrary commits — which is exactly the gap Compare Versions fills.

1
Every diff lands in an editor tab

Today every file diff opens as a native VS Code diff tab in the main window. There is no window story, and no user-facing settings at all — the extension currently contributes zero configuration options.

The constraint. VS Code has no “floating dialog” primitive the way a desktop IDE does. The closest real equivalent is an auxiliary window — a detached OS window that hosts editor groups. Everything in feature 2 is designed around that, and it is the single biggest thing to validate before building. See Risks.
01

Compare Versions

Select two commits anywhere in the log, right-click, and see the accumulated difference between them as a single set of changed files — the same action IDEA offers when a two-commit selection is active.

Behaviour rules

When it shows
  • Visible whenever the menu is opened on a multi-commit selection.
  • Enabled only when exactly two commits are selected.
  • Hidden entirely for a single-commit selection.
What it compares
  • Always older → newer, regardless of click order, so the result reads the way the history reads.
  • The net difference between the two snapshots — not a per-commit union. Work added and then reverted between them correctly shows as no change.
  • Merge commits are treated as their snapshot, not their parents.

What opens

A Changes window listing every file that differs between the two commits — the same window feature 2 introduces. The two features share one surface; building them together is cheaper than building either alone.

02

Floating diff windows

Diffs stop competing with your code for editor real estate. A changes list opens in its own detached window; double-clicking a file opens a second window beside it, and every subsequent double-click replaces that window's content rather than piling up tabs.

The two-window model

The diff window

The setting

This changes where every diff in the extension lands, so it must be a preference — and the extension has no settings today, so this introduces the first one.

Settings — IDEA Git
Open diffs in
Where file diffs are shown when you open one from the Git Log, a comparison, or the Commit panel.
Floating windowDefaultA detached window, reused for every diff. Closest to the IDEA behaviour.
Editor tabToday's behaviour — a diff tab in the main window.
Why default to floating
  • It is the behaviour you asked for and the one the fork exists to provide.
  • The escape hatch is one setting away, and the old behaviour is preserved intact behind it — nothing is removed.
  • Both windows degrade gracefully: if a detached window cannot be created, the same content opens as an editor tab and the user sees a one-time notice rather than a failure.

Rebrand to IDEA Git

The fork is already detached; the identity has not caught up. Roughly 250 occurrences of the old name span the manifest, command identifiers, webview panel types, error types and docs. This is mechanical work, but two parts of it are user-visible and irreversible.

04

Risks worth knowing before we start

Ordered by how much they could change the shape of the work.

Highest

Detached windows are not fully under our control

VS Code decides how detached windows are created, positioned and restored; an extension can request one but cannot size or place it the way a desktop IDE can. Expect the windows to look right and behave right, but not to remember an exact position. Worth a throwaway spike on day one before committing to the default.

High

“Reused window” has edge cases

What happens when the user closes the diff window, then double-clicks again? When two comparisons are open at once — do they share one diff window or get one each? Proposed answer: reopen on demand, and one diff window globally, matching the IDEA behaviour in your screenshots. Flag it if you want per-comparison windows instead.

Medium

Minimum VS Code version rises

Detached windows are not available in the oldest versions the extension currently claims to support. The manifest's minimum version will need to move up, which drops support for older installs — including some Cursor builds, which track VS Code with a lag.

Medium

Two commits can be far apart

Comparing commits thousands apart produces a very large file list. The window needs to stay responsive and cancellable, and should say plainly when a comparison is still being computed rather than appearing to hang.

06

Suggested order

Front-loaded so the riskiest assumption gets tested before anything is built on top of it.

First

Prove the window

A throwaway spike: open a diff in a detached window and confirm it behaves. If it doesn't, feature 2 changes shape and it's better to know on day one.

Then

Windows & setting

The changes window, the reusable diff window, the preference, and the fallback to an editor tab. Feature 1 has somewhere to open into once this lands.

Then

Compare Versions, then rebrand

The menu action is small once the surface exists. The rename goes last — it touches every file, and doing it last keeps the feature diffs readable.
